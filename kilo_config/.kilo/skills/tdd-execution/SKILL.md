# TDD 执行模板

## 何时触发

- 新功能实现
- Bug 修复
- 行为变更（输入输出/异常/边界变化）
- 重构（已有测试保护时）

## 执行步骤

### Step 1: 红（写失败测试）

1. 为本次改动写**一个**失败测试。
2. **看着它失败**，记录失败消息和堆栈。
3. 如果测试一写就通过：
   - 说明测试没有真正覆盖本次改动
   - 修改测试输入/断言，使其必然失败
   - 重新运行，确认失败
4. 记录：`[RED] 测试名 | 失败原因`

### Step 2: 绿（最小实现）

1. 写**最小**代码让测试通过。
2. 禁止：提前写未来功能、引入未使用的抽象、优化性能。
3. 运行测试，确认通过。
4. 记录：`[GREEN] 改动文件:行号 | 改动摘要`

### Step 3: 重构（保持绿）

1. 消除重复、改善命名、提取函数。
2. 每改一步跑测试，保持绿。
3. 若变红，立即回滚到上一步绿状态。
4. 记录：`[REFACTOR] 改动文件:行号 | 重构摘要`

## 测试用例设计模板

每个被测功能必须覆盖：

| 类别 | 示例 | 必填 |
|------|------|------|
| 正常路径 | 标准输入 → 预期输出 | 是 |
| 空值/零值 | null / 0 / "" / [] | 是 |
| 边界值 | 最小值、最大值、长度边界 | 是 |
| 异常路径 | 非法输入、越权、超时、网络失败 | 视功能 |
| 并发/竞态 | 多线程/异步冲突 | 视功能 |

## 无测试套件项目

若项目没有测试框架：

1. 至少补一条**手动验证脚本**（shell/python/node），覆盖正常路径 + 一个边界。
2. 脚本输出显式 SUCCESS/FAIL，不能只是打印日志。
3. 将脚本路径写入验收映射表"验证方式"列。

## 反模式

- `[TDD_ANTI_PATTERN_SKIP_RED]`：跳过"看着它失败"直接写实现。
- `[TDD_ANTI_PATTERN_BIG_STEP]`：一步写多个测试或大量实现。
- `[TDD_ANTI_PATTERN_NO_ASSERT]`：测试没有明确断言或没有失败分支。
