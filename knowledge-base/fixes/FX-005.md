## 症状

- 对**同一单元**（同一目标文件/同一 task_context 字段）在单条消息中并行发起多个相同 `task` 调用（如 U9 重派时一次发 20+ 个相同 coder）。
- 多个 subagent 并发写同一文件（如 AGENTS.md），返回互相冲突的字节数（3684/5370/5952/6110/6386/6478/6515/7238），磁盘最终状态不可信。
- 并发写 task_context 导致 rename ENOENT，task_context 文件丢失，需重新 init。
- 大量重复调用造成 token 严重浪费 + 会话卡死。

## 根因

编排失误：把「并行派发」错误地用于**同一单元**。铁律 #11 的并行策略只适用于**不同单元**（无 after 依赖的独立单元），同一单元必须**串行单派**。口头承诺（"每个单元只派 1 个 task"）无法机械杜绝复发——需要行为纪律 + 经验沉淀双保险。

## 修复

1. **同一单元只派 1 个 task**：重派前先确认该单元无 in-flight 的 task；有则等其返回，不重复发起。
2. **并行仅限不同单元**：铁律 #11 并行组只装无依赖的独立单元，同一目标文件/字段绝不进同一并行组。
3. **并发写防护**：task_context 写入经 `task-context.mjs` 收口，禁止多个 subagent 同时 set 同一字段；文件类目标（AGENTS.md 等）同一时刻只允许一个 coder 写。
4. **重派前验证磁盘态**：对并发写过的文件，先 `grep` + 字节数确认最终态，再决定是否重派，不盲目重发。
5. **沉淀经验**：此类编排事故按 reflection.md 强制跨会话根因回溯，写入 knowledge-base/fixes/。

## 复验

- `rg -n "同一单元|重复派发" knowledge-base/fixes/FX-005.md` 命中。
- 后续任务中同一单元 dispatch_log 无重复条目（每单元 ≤1 次派发，重派仅限 fail/timeout 后）。
- 无并发写导致的 task_context 丢失 / 文件字节数冲突复发。
