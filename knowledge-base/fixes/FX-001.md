## 症状

- verifier/reviewer 作为子代理（`task` 工具）被派发执行检查，返回过程中出现 `Tool execution aborted`（工具执行被中止）。
- 子代理在跑工具（grep/run/read）时被中断，没有返回任何 result，或返回不完整。
- 主会话只看到「会话断开 / 工具被中止」，看不到明确结论。
- 若处理不当：把 abort 误当"成功"、或直接重跑同症状、或跳过硬性验证门。

## 根因

`Tool execution aborted` 在框架语义中等于**该并行组/该工具调用被中止**，等价于会话断开——并非"已完成、验证通过"。任何把「工具被中止」解读为「该 agent 验证成功」的做法都是信任传递，违反 AGENTS.md「禁止信任传递 / 自验无效」硬规则。中止后原 agent 的状态不可用，不能以其返回充当验收证据。

## 修复

按 `lifecycle/graph.yaml` + `agent/conductor.md` 节点 `on_fail` 派发处理，不把 abort 当成功：

1. **确认中止点**：识别是哪个并行组、哪个工具调用被 abort。并行组内其它结果作废，不得拼接为"已验证"。
2. **节点 on_fail 派发**：中止视为该节点失败，按拓扑 on_fail 规则重新派发对应智能体（verifier/reviewer 重派独立重跑），保证验证是**独立重跑**而非沿用旧结论。
3. **跨会话根因回溯**：进入 `reflection.md`「强制跨会话根因回溯」，先跑 `kilo_local_recall` 搜历史同类，再检索 knowledge-base（命中打 `[KB_HIT]`）。
4. **工程化防 abort 门禁**：遵守 conductor 铁律 #9 的 step 0/1/2 + 并行安全边界，避免再次触发 abort（控制并行规模、严格委派包 ≤4000 字符、subagent 返回 ≤4000 字符）。

## 复验

- abort 节点已按 on_fail 重新派发，且**独立重跑**通过（非沿用旧 abort 前的中间态）。
- 返回契约无 `[PROCESS_VIOLATION]`；无「把 abort 当成功」的信任传递残留。
- `rg -n "C:\\Users|E:\\AI"` 检查本次改动文件无硬编码盘符。
