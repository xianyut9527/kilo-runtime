## 症状

- 做「去掉冗余/无意义内容」类清理时，按目录名或「看起来是空的/是临时产物」判断就批量删除，结果删掉了 git **已跟踪**的历史产物（本次：`reports/2026-08-12/*` 两份基准审计报告）。
- 删完 `git status --porcelain` 才出现成批 ` D ` 条目——清理动作与用户的改动混在同一次 diff 里，回滚成本被放大。
- 空目录（`monthly-report/`、`weekly-report/`）删了也会「消失」，让人误以为前面的删除同样安全。

## 根因

1. **判定依据错了**：用文件系统观感（是否为空、名字像不像产物）替代了「git 是否跟踪」这一唯一权威信号。仓库里的 `reports/`、`docs/` 是**有归档惯例的交付物**，不是构建产物。
2. **批量删除没有 dry-run**：一条命令覆盖多个路径，缺少「先列清单、再执行」的两步，出错时无法定位是哪一路径越界。
3. 构建产物/临时物与已跟踪物在同一棵目录树里混放（`.tmp`、`__pycache__`、`reports/` 并存），肉眼分类必然出错。

## 修复

1. **删除前三步硬顺序**（任何批量清理都适用）：
   - `git ls-files -- <path>`：有输出 = 已跟踪 → **不许直接删**；确属废弃走 `git rm -r -- <path>`（在 diff 里显式表达删除意图），否则保留；
   - 无输出且命中 `.gitignore` → 才是可安全删除的本地产物；
   - 空目录另用 `git ls-files` 判定：git 不跟踪空目录，删了不影响他人，但也**不会有门禁发现你删错**。
2. **批量清理先 dry-run**：先把候选路径完整打印（`git status --porcelain` / 文件清单），人工或门禁确认边界后再执行；禁止「一条 rm 扫多个不相关目录」。
3. **误删即时回滚**：未 staged 用 `git restore -- <path>`（或 `git checkout -- <path>`）；已 staged 用 `git restore --staged --worktree -- <path>`。回滚后 `git status` 应只剩本次真实改动。
4. **清理动作与功能改动分离提交**：删除类改动单独成一次 diff，避免混在大改动里被忽略。

## 复验

- `rg -n "git ls-files" knowledge-base/fixes/FX-014.md` 命中。
- 一次清理批次收口后 `git status --porcelain` 中 ` D ` 条目数 = 计划内删除数（`git diff --diff-filter=D --name-only` 与之逐条对得上）。
- 误删场景：`git restore <path>` 后 `git status --porcelain <path>` 无输出。
