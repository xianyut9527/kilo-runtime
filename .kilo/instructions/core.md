# Core Runtime Rules

## 语言与沟通

- 始终使用用户提问的语言回复。
- 识别明显错别字或术语误写，纠正后再执行，并在回复中简要标注纠正内容。
- 需求存在歧义、缺少关键信息或置信度不足时，先一次性澄清，不基于猜测编码。
- 先说假设和可选方案，再开始实现；优先选择更简单的路径。

## 意图识别

- 用户请求按操作性质分为两类：
  - **咨询类**：仅需分析/建议/方案（如"给个建议""分析一下""怎么优化""评价""能不能"等）。此类请求**只输出结论和方案，禁止修改任何文件**。
  - **执行类**：需要实际修改代码/配置（如"帮我改""修复""实现""添加""删除"等）。此类请求按正常流程编码。
- 识别信号：用户使用了咨询性/探讨性语言而非明确的执行指令时，默认归类为咨询类。
- 边界模糊时（无法判断是咨询还是执行）：先输出分析，主动询问"是否需要我直接实施？"，待用户确认后再动手。
- **最大化尊重用户意愿**：用户明确要求"只给建议""点到为止""不要改代码"时严格遵守，不画蛇添足。

## 实施原则

- 先读后写，禁止基于猜测修改代码或配置。
- 只做完成目标所必需的最小改动，避免顺手重构或风格化清理。
- 保持项目既有风格和分层；只清理因本次修改直接产生的无用代码。
- 不做投机性扩展，不为未来可能性预埋抽象、开关或配置。
- 涉及调用链、状态流、数据流、配置流或根因不明确的问题，先定位再修改；未完成定位前不直接开修。

## 复用与分层

- 编码前必须先搜索现有实现，优先复用已有工具函数、组件、hooks、services、类型与常量。
- 若已有实现覆盖需求至少 80%，直接复用或在原处扩展，禁止重复实现。
- 纯工具逻辑、复用逻辑、接口访问逻辑与视图渲染职责应按项目现有分层和命名规范归位；若项目无明确约定，优先遵循“低耦合、单一职责、易复用”的组织方式。

## 诊断优先级

- 先判断问题属于哪一类，再沿对应链路逐层下钻；不要平均撒网。
- 未排除上游前，不优先修改下游表现层；后面的异常往往只是前面异常的结果。

### 数据类问题

- 默认顺序：`输入/参数 -> 数据源或请求 -> 解析/映射 -> 过滤/聚合/排序/格式化 -> 状态或缓存 -> 派生逻辑 -> 组件渲染`
- 常见信号：数据不对、列表异常、统计不准、展示值错误、接口看起来正常但页面结果不对。
- 默认不先怀疑组件；只有在上游链路基本正常时，才提高组件层优先级。

### UI / 样式类问题

- 默认顺序：`样式变量/主题 -> className 或选择器 -> 布局容器 -> 条件渲染 -> DOM 结构 -> 数据回退`
- 常见信号：错位、遮挡、间距异常、响应式异常、主题不生效、视觉状态不一致。
- 默认不先排查数据处理，除非界面异常明显由错误数据驱动。

### 交互类问题

- 默认顺序：`事件绑定 -> 事件处理函数 -> 状态更新 -> 副作用 -> 重新渲染`
- 常见信号：点击没反应、按钮状态不对、弹窗不开、表单提交无效。

### 网络 / 接口类问题

- 默认顺序：`请求触发 -> 请求参数/载荷 -> 认证与请求头 -> 响应状态 -> 响应解析 -> 下游状态`
- 常见信号：401/403/500、接口失败、接口成功但功能异常、字段不匹配。

### 状态类问题

- 默认顺序：`写入路径 -> store/context/cache -> 失效与同步 -> 派生状态 -> 订阅方/渲染`
- 常见信号：旧数据、刷新后异常恢复、局部更新不同步、缓存污染。

### 性能类问题

- 默认顺序：`数据规模 -> 昂贵转换 -> 重复状态写入 -> 重渲染 -> 布局与重绘`
- 常见信号：卡顿、输入延迟、滚动抖动、CPU 飙升、频繁无效更新。

## 验证与安全

- 修改后必须执行可用的测试、构建、类型检查、Lint；格式化仅限变更文件。
- 禁止暴露密钥、Token、API Key 等敏感信息；敏感配置通过环境变量注入。
- 涉及资金、安全或核心逻辑的变更，必须经过独立审查。

## 大文件策略

- 先搜索定位，再局部读取；避免一次性通读大文件。
- 优先增量编辑，不整文件重写。
