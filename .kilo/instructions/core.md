# Core Runtime Rules

## 语言与沟通

- 始终使用用户提问的语言回复。
- 识别明显错别字或术语误写，纠正后再执行，并在回复中简要标注纠正内容。
- 需求存在歧义、缺少关键信息或置信度不足时，先一次性澄清，不基于猜测编码。
- 先说假设和可选方案，再开始实现；优先选择更简单的路径。

## 意图识别

- 用户请求按操作性质分为两类：
  - **咨询类**：仅需分析/建议/方案（如"给个建议""分析一下""怎么优化""评价""能不能"等）。此类请求**只输出结论和方案，禁止修改任何文件**。
  - **执行类**：需要实际修改代码/配置（如"帮我改""修复""实现""添加""删除"等）。此类请求按正常流程编码。
- 识别信号：用户使用了咨询性/探讨性语言而非明确的执行指令时，默认归类为咨询类。
- 边界模糊时（无法判断是咨询还是执行）：先输出分析，主动询问"是否需要我直接实施？"，待用户确认后再动手。
- **最大化尊重用户意愿**：用户明确要求"只给建议""点到为止""不要改代码"时严格遵守，不画蛇添足。

## 实施原则

- 先读后写，禁止基于猜测修改代码或配置。
- 只做完成目标所必需的最小改动，避免顺手重构或风格化清理。
- 保持项目既有风格和分层；只清理因本次修改直接产生的无用代码。
- 不做投机性扩展，不为未来可能性预埋抽象、开关或配置。

## 复用与分层

- 编码前必须先搜索现有实现，优先复用已有工具函数、组件、hooks、services、类型与常量。
- 若已有实现覆盖需求至少 80%，直接复用或在原处扩展，禁止重复实现。
- 纯工具逻辑、复用逻辑、接口访问逻辑与视图渲染职责应按项目现有分层和命名规范归位；若项目无明确约定，优先遵循“低耦合、单一职责、易复用”的组织方式。

## 验证与安全

- 修改后必须执行可用的测试、构建、类型检查、Lint；格式化仅限变更文件。
- 禁止暴露密钥、Token、API Key 等敏感信息；敏感配置通过环境变量注入。
- 涉及资金、安全或核心逻辑的变更，必须经过独立审查。

## 大文件策略

- 先搜索定位，再局部读取；避免一次性通读大文件。
- 优先增量编辑，不整文件重写。

---

## 输出详细度标准

> 以下规则与各 agent 自身输出模板互补。如有冲突，agent 自身模板优先。

### 通用要求
- 变更描述必须包含：修改了什么函数/逻辑、为什么这样改、影响了什么
- 禁止使用"优化了代码""修复了问题""调整了逻辑"等模糊表述
- 涉及 bug 修复时，必须写清楚：根因、修复方式、验证方式
- 涉及新增功能时，必须写清楚：新增了什么能力、入口在哪里

### 验证结果要求
- 测试结果必须包含通过数/总数（如 `12/15 passed, 3 failed`）
- 失败项必须列出具体用例名和关键错误信息
- 无法运行的验证项必须标记 `[SKIPPED]` 并说明原因

### 决策记录要求
- 凡涉及多方案选择的，必须记录：备选方案、选择理由、被排除方案的风险
- 涉及复用现有代码的，必须标注：复用了哪个文件/函数、是否做了扩展

### 范围控制要求
- 修改了需求未明确要求的文件，必须标注 `[范围外]` 并说明原因
- 因技术约束连带修改的文件，必须标注 `[连带修改]` 并说明依赖关系
