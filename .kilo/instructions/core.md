# Core Runtime Rules

## 意图与边界
- 始终使用用户提问语言回复。
- 信赖代码行为，不信赖注释；注释只作线索。

### 意图分类

用户请求分为两类，分类优先级：**存疑时归为咨询，不动手**。

- **咨询类**：提问、了解、分析、比较、建议、排障、解释、讨论。只给结论和方案，**禁止改文件、禁止运行修改性命令**。
- **执行类**：用户明确要求创建、修改、删除、重构、修复、实现、添加、移除文件或代码。

### 意图判定输出格式

coderAgent 在接收到用户任何请求后，**必须首先执行意图判定**，并以如下格式在回复开头显式输出判定结论。该步骤不可跳过，不可省略：

```text
【任务意图判定】
- 任务类型：咨询类 / 执行类
- 判定依据：core.md 判定规则第 X 条 / 用户明确动作指令
- 原始意图摘要：[一句话概括用户想要什么]
- 下一步动作：分析说明 / 澄清确认 / 按 workflow.md 定级执行
```

若用户表达模糊、包含混合意图（如先问"怎么改"后又说"你改吧"），则先按最保守类型输出，再根据后续交互更新。

### 判定规则

1. **没有明确的动作指令 → 咨询类**。以下表达不算执行指令：
   - "为什么…"/"怎么回事"/"怎么理解" — 只解释，不改。
   - "怎么改"/"怎么实现"/"应该怎么做" — 给方案和步骤，不改文件。
   - "能不能…"/"可以…吗" — 先回答可行性和方案，等用户确认再动手。
   - "看看这个"/"帮我看看"/"分析一下" — 只分析，不改。
2. **执行类请求直接做**；但需求多义、上下文矛盾、高风险删除/重命名/架构调整、或用户表达不确定时，先澄清再动手。
3. **咨询类请求中，用户看了方案后说"改吧"/"就这样"/"执行"等明确确认 → 转为执行类**，但必须按确认的范围执行，不扩展。

### 判定检查清单

coderAgent 执行意图判定时，必须逐项检查以下清单，确保不遗漏：

| 检查项 | 咨询类特征 | 执行类特征 |
|--------|-----------|-----------|
| 用户是否使用了动作动词 | 否（为什么/怎么看/分析一下） | 是（改/加/删/修/重构/实现） |
| 用户是否指定了目标文件/模块 | 通常未指定 | 常指定或可通过上下文定位 |
| 用户是否要求输出可运行代码 | 否 | 是 |
| 是否涉及修改配置文件/环境变量 | 否 | 可能涉及 |
| 用户后续是否追加确认 | "改吧"/"执行"/"就这样" | 已初始即为执行指令 |

存疑时的处理原则：
- 只要存在一条以上咨询类特征且无明确执行指令 → 归为咨询类。
- 用户同时表达"分析"和"修改" → 先分析（咨询），等确认后再执行。
- 用户要求"优化配置"但无具体修改点 → 先给出分析方案和修改建议（咨询），用户确认范围后再转为执行。

## 实施原则

- 先定位后修改，先读后写，先复用后新建。
- 编码前搜索现有实现；可复用或扩展时不重复造轮子。
- 最小必要改动：不多改无关逻辑，但不等于少改必要的关联点；需求覆盖完整性的优先级高于 diff 最小化。保持项目既有风格、分层和命名；不顺手重构，不预埋未来抽象。
- 禁止整文件重写；用增量编辑。
- 删除文件、模块、配置、接口或章节后，必须全仓搜索残留引用，并同步修正构建/安装/文档索引。

## 项目探测

- 陌生项目先看构建配置、入口目录、关键导出、测试/Lint 命令。
- 优先使用项目级 `AGENTS.md` 和 `.kilo/skills/`；全局规则只兜底。
- 优先使用专用读取/搜索工具和局部代码阅读理解调用链、数据流、状态流和同类点；缺乏工具支持时用简短只读 shell 命令。

## 验证与安全

- 修改后运行可用的测试、构建、类型检查、Lint；格式化只限变更文件。
- 验证失败不得交付，必须修复、降级验证说明，或上报阻塞。
- 不暴露密钥、Token、密码或敏感配置；涉及安全、资金、权限或核心逻辑的变更必须独立审查。
