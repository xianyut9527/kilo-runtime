# Failure Reflection Protocol

## [META] 协议定位

本协议定义失败反思机制（Failure Reflection Protocol），适用于以下场景：

- 单模型自修复循环中修复未达预期
- 委派子智能体后返回结果不满足验收标准
- 用户反馈与预期偏差
- 任何"再试一次"之前

### 核心原则

> **反思先于升级。** 在切换到更强智能体或并行模式之前，必须先逐层反思当前失败的根本原因。盲目升级会掩盖诊断错误、方案偏差或意图误解，导致更高成本的低质量交付。

[MUST] 当修复/实现未达预期时，执行本协议定义的 L0→L4 逐层反思，确认当前层级无问题后再升级。

---

## 触发条件

### 触发信号矩阵

| 信号类别 | 信号描述 | 典型表现 | 起始反思层级 | 不计入失败轮次 |
|---------|---------|---------|------------|-------------|
| 重复失败 | 同一任务执行 ≥2 次仍未通过验证 | 测试持续失败、构建报同样错误、同一文件反复修改无效 | L0（首次）/ L0→L1（再次） | L0 明确命中时不计数 |
| 发散失败 | 每次修复引入了新的不同错误 | 修 A 坏 B、修复一个测试却破坏了另一个、构建报错每次不同 | L2 | 否 |
| 用户质疑 | 用户主动质疑结果、方向或理解 | "还是不对""你没理解我的意思""为什么这样做""不是我要的" | L3 | 是 |
| 模式异常 | 执行流程出现反常行为 | 命令反复超时、文件写入后读取为空、工具调用返回异常、上下文窗口急剧缩小 | L0 | 否 |

### 信号优先级

当多个触发信号同时出现时，按以下优先级确定起始层级：

1. **用户质疑**（最高优先）→ 从 L3 起步
2. **发散失败** → 从 L2 起步
3. **模式异常** → 从 L0 起步
4. **重复失败** → 按失败轮次递进

## 反思层级

### 层级概览

```
L0 → L1 → L2 → L3 → L4
操作    诊断   策略   理解   上下文
  │      │      │      │       │
  │      │      │      │       └─ 关键信息遗漏
  │      │      │      └─ 用户意图理解偏差
  │      │      └─ 解题思路/方案错误
  │      └─ 根因诊断错误
  └─ 动手执行错误（写错/删错/用错）
```

---

### L0 操作层

> **核心问题：我的执行是否正确？**

| 自检项 | 检查要点 | 典型证据 |
|--------|---------|---------|
| L0.1 文件目标 | 是否写入了正确的文件路径？是否存在路径拼写错误或工作目录错误？ | 检查 `read`/`write`/`edit` 操作的文件路径 |
| L0.2 语法与格式 | 修改后的代码是否存在语法错误、缩进异常、引号不匹配？ | 编译错误输出、lint 报错、diff 片段的语法高亮异常 |
| L0.3 工具使用 | 是否用错了工具（如该用 `edit` 却用了 `write`）、命令参数错误、超时设置不当？ | 工具返回的错误信息、命令的 exit code |
| L0.4 环境问题 | 构建/测试/Lint 命令本身是否能正常运行？依赖是否安装？端口是否占用？ | 裸跑命令（不含本次修改）的结果 |

- **修正成本**：低。通常 1 步即可修复。
- **是否可自主修复**：是。
- **命中后的行动**：立即修正操作错误，重新执行任务。**不进入 L1。**
- **失败轮次计数规则**：若明确命中 L0（如文件路径写错、语法错误、命令参数错误），本轮不计入失败轮次。仅当 L0 未命中或 L0 修复后仍失败，才计为有效失败轮次。

---

### L1 诊断层

> **核心问题：我的根因诊断是否正确？**

| 自检项 | 检查要点 | 典型证据 |
|--------|---------|---------|
| L1.1 问题类型判断 | 是否将问题归类到了正确的类别（数据/UI/交互/网络/状态/性能）？ | 对照 `core.md` 诊断优先级表中的"信号"列，验证当前分类是否匹配实际现象 |
| L1.2 排查链路方向 | 是否按正确链路逐层下钻？是否跳过了上游直接修了下游？ | 对照 `core.md` 排查链路列，检查是否按序排查 |
| L1.3 混淆类别排除 | 是否排除了易混淆的类别？ | 对照 `core.md` 易混淆类别快速锚定表，逐条验证 |
| L1.4 治标还是治本 | 当前修复是解决了根因还是只掩盖了症状？ | 验证修复是否覆盖了数据源头/状态写入/事件绑定等上游环节 |

- **修正成本**：中。需要重新诊断并可能回退之前的无效修改。
- **是否可自主修复**：多数情况下可，但需先撤销无效修改再按正确诊断重新修复。
- **命中后的行动**：
  1. 输出正确的诊断结论（问题类型 + 根因 + 证据链路）
  2. 回退基于错误诊断的修改
  3. 按正确诊断重新实施修复

---

### L2 策略层

> **核心问题：我的解题思路/方案是否正确？**

| 自检项 | 检查要点 | 典型证据 |
|--------|---------|---------|
| L2.1 方案是否过度复杂 | 是否引入了不必要的抽象、新建了不必要的新文件、使用了过于迂回的实现方式？ | 对比项目现有类似功能的实现模式，判断复杂度是否匹配 |
| L2.2 方案是否引入新问题 | 修复是否破坏了现有功能、影响了不相干的模块、引入了副作用？ | 新出现的测试失败、类型错误、lint 警告 |
| L2.3 是否忽略了更简单的解法 | 是否存在更直接、复用度更高、diff 更小的替代方案？ | 搜索项目内是否有已存在的工具函数/组件可直接复用（≥80% 需求覆盖） |
| L2.4 方案是否符合项目架构 | 修改是否放在了正确的层？是否违反了项目既有的分层约定和依赖方向？ | 对照项目级 `AGENTS.md`、`.kilo/skills/` 中的架构说明 |

- **修正成本**：中高。可能需要回退整个方案并重新设计。
- **是否可自主修复**：部分可。若能在现有方案基础上微调则自主修复；若需根本性重设计，应在反思报告中说明备选方案并建议升级到 `architect`。
- **命中后的行动**：
  1. 撤销当前方案的修改
  2. 给出替代方案（至少 2 个，含优劣势对比）
  3. 若替代方案涉及架构变更，停止并上报

---

### L3 理解层

> **核心问题：我对用户意图的理解是否正确？**

| 自检项 | 检查要点 | 典型证据 |
|--------|---------|---------|
| L3.1 需求是否被误解 | 输出的结果是否与用户的明确要求不同？是否在解决另一个问题？ | 逐条对照用户原始需求与实现结果，标注匹配/偏差项 |
| L3.2 隐含需求是否遗漏 | 用户未明说但上下文暗示的约束（如"保持现有风格""不要改其他文件""必须兼容旧版"）是否被忽略？ | 重新阅读对话历史，提取未在实现中体现的约束 |
| L3.3 需求歧义是否未澄清 | 是否存在当初应该问但没问的模糊点，而这些模糊点恰好导致了当前失败？ | 列出所有可多义解读的需求点，标注当前理解和可能的其他理解 |
| L3.4 用户反馈信号是否被正确解读 | 用户说"还是不对""再看看"等反馈时，是否真正理解了用户不满意的点？ | 重新分析用户反馈的上下文，判断是否遗漏了关键信号 |

- **修正成本**：高。可能需要重新理解需求、重新设计方案。
- **是否可自主修复**：取决于 agent mode（见 [Agent Mode 差异处理](#agent-mode-差异处理)）。
- **命中后的行动**：
  - **all-mode agent**：直接向用户一次性澄清所有歧义点（不逐条追问），暂停修复
  - **subagent**：将澄清问题写入反思报告上报调用方，不自行业主确认
  - [MUST NOT] 在 L3 命中后继续向下执行代码修改

---

### L4 上下文层

> **核心问题：我是否遗漏了关键上下文？**

| 自检项 | 检查要点 | 典型证据 |
|--------|---------|---------|
| L4.1 项目约定是否遗漏 | 是否忽略了项目级 `AGENTS.md`、`.kilo/skills/`、`.kilo/commands/` 中的关键约束？ | 重新读取项目级上下文文件，对照实现检查遗漏项 |
| L4.2 隐藏依赖是否被忽略 | 修改的代码是否触发了未预期的跨模块影响、配置联动、环境变量依赖？ | 搜索被修改符号的所有引用方、导入方，检查是否受影响 |
| L4.3 跨模块影响是否评估 | 修改是否影响了其他未被考虑的模块、路由、页面、API？ | 使用 `grep` 搜索被修改的导出符号的所有消费方 |
| L4.4 运行环境假设是否正确 | 是否假设了错误的目标平台、Node 版本、浏览器兼容性、操作系统？ | 检查 `package.json` 的 engines 字段、`tsconfig.json` 的 target、项目文档中的环境要求 |

- **修正成本**：很高。可能需要重新理解项目全局架构和依赖关系。
- **是否可自主修复**：否。所有 agent 统一处理。
- **命中后的行动**：
  - [MUST] 暂停当前任务
  - [MUST] 将缺失的上下文和影响评估写入反思报告
  - [MUST] 上报调用方（或用户），不再继续向下执行
  - [PREFER] 建议升级到 `architect` 或在补充上下文后重新委派

## 递进规则

### 失败轮次与反思深度映射

| 当前失败轮次 | 执行层级范围 | 说明 |
|------------|------------|------|
| 第 1 次 | L0 only | 先排除明显的操作失误 |
| 第 2 次 | L0 → L1 | L0 未命中或修复后仍失败，上探诊断层 |
| 第 3 次 | L0 → L2 | L1 未命中或修正后仍失败，上探策略层 |
| 第 4 次及以上 | L0 → L4（完整） | 逐层全量反思 |
| L0 修正后不计轮次 | 不推进 | 语法错误/路径错误等纯操作失误修正后，计为同一轮 |

### 特殊规则

- **用户质疑信号**：无论当前处于第几轮失败，直接覆盖为从 L3 起步检查
- **发散失败信号**：无论当前处于第几轮失败，直接覆盖为从 L2 起步检查
- **L3/L4 命中即停止**：一旦 L3 或 L4 确认命中，不再向下执行，直接进入反思报告输出

### 层间关系

```
L0 通过 → 进入 L1（如当前深度允许）
L0 命中 → 修正 → 重试（不计轮次）
L1 通过 → 进入 L2（如当前深度允许）
L1 命中 → 输出诊断修正 → 按新诊断重试
L2 命中 → 输出策略调整 → 撤销当前修改 → 按新方案重试
L3 命中 → 输出澄清问题 → 暂停（不再重试）
L4 命中 → 输出上下文缺失 → 暂停 → 上报
```

## Agent Mode 差异处理

### 模式分类

| Agent | 模式 | L3 处理 | L4 处理 |
|-------|------|---------|---------|
| coderAgent | all | 直接向用户输出澄清问题列表 | 暂停并上报给用户 |
| ensemble | all | 直接向用户输出澄清问题列表 | 暂停并上报给用户 |
| engineer | subagent | 写入反思报告上报调用方 | 暂停并上报调用方 |
| fixer | subagent | 写入反思报告上报调用方 | 暂停并上报调用方 |
| architect | subagent | 写入反思报告上报调用方 | 暂停并上报调用方 |
| reviewer | subagent | 写入反思报告上报调用方 | 暂停并上报调用方 |
| checker | subagent | 写入反思报告上报调用方 | 暂停并上报调用方 |
| executor-A/B/C | subagent | 写入反思报告上报调用方 | 暂停并上报调用方 |
| synthesizer | subagent | 写入反思报告上报调用方 | 暂停并上报调用方 |

### all-mode 行为细则

1. L0-L2 命中 → 自主修正后重试（L0 不计轮次）
2. L3 命中 → [MUST] 输出完整的澄清问题列表和反思报告，[MUST NOT] 继续执行代码修改。[PREFER] 一次性提出所有澄清问题而非逐条追问。
3. L4 命中 → [MUST] 暂停并输出反思报告，[MUST NOT] 继续执行

### subagent 行为细则

1. L0-L2 命中 → 在 subagent 权限范围内自主修正后重试
2. L3 命中 → [MUST] 将澄清问题写入反思报告的 L3 结论字段，[MUST NOT] 自行向用户发起澄清。将反思报告随失败结果一并上报调用方（coderAgent / ensemble）
3. L4 命中 → [MUST] 暂停，将反思报告上报调用方
4. [MUST NOT] 在 subagent 模式下跳过反思直接返回失败——调用方需要完整的反思报告来判断是否升级

### 通用约束

- 所有 agent 在 L3/L4 命中后 [MUST NOT] 继续向下执行代码修改
- 反思本身不应影响工作目录中的文件（反思报告为输出内容，不写入文件系统）
- subagent 的反思报告 [MUST] 包含在返回给调用方的结果中

## 与现有机制的引用关系

### 引用 `core.md` 的诊断优先级表 → L1 自检

L1 诊断层的自检项 L1.1、L1.2、L1.3 直接引用 `core.md` 第 2 节"诊断优先级"：

- **L1.1** 对照 `core.md` 诊断优先级表的"类别"与"信号"列 → 验证当前问题分类是否匹配
- **L1.2** 对照 `core.md` 诊断优先级表的"排查链路"列 → 验证是否按序下钻
- **L1.3** 对照 `core.md` "易混淆类别快速锚定"子表 → 逐条排除易混淆类别

### 引用 `workflow.md` 的升级条件 → 升级前置约束

`workflow.md` 第 3 节定义了"何时升级到 Ensemble"的 5 个条件。本协议作为升级的**前置门禁**：

- 在满足 `workflow.md` 升级条件之前，[MUST] 先完成本协议定义的反思
- 若反思发现根因在 L0-L2 且可自主修复，则不触发升级
- 若反思确认根因在 L3-L4 或 L0-L2 无法自主修复，则输出反思报告后触发升级
- 升级时将反思报告作为委派上下文的一部分传递给 ensemble

### 引用 coderAgent 的语义检测 → 触发信号

coderAgent 在接收用户输入时执行的语义分析（识别"还是不对""改了很多次""深度分析""还有遗漏"等质疑信号）直接映射到本协议的"用户质疑"触发信号，进入 L3 起步的反思流程。

### 引用 `AGENTS.md` 的智能体清单 → Agent Mode 分类

`AGENTS.md` "智能体清单"中定义的每个智能体的模式（all/subagent）即为本协议中 Agent Mode 差异处理的分类依据。

## 约束与边界

### 强制约束

- [MUST] L3 或 L4 命中后，立即停止所有代码修改操作，不再继续向下执行
- [MUST] 每层自检必须附证据（代码片段/命令输出/文件引用/搜索结果），无证据的结论视为无效
- [MUST] L0 明确命中（语法错误/路径错误/命令参数错误）不计入失败轮次
- [MUST] L3/L4 命中后，subagent 不得自行向用户发起澄清，必须通过反思报告上报
- [MUST] 反思本身不写入文件系统（不创建/修改任何文件），反思报告为纯输出内容
- [MUST NOT] 在未完成当前深度反思前就启动升级流程

### 步骤预算

| 约束项 | 预算 |
|--------|------|
| 每层自检最大步骤数 | 3 steps |
| 反思总最大步骤数 | 15 steps（5 层 × 3 steps） |
| 步骤预算不足时 | 将已完成层的反思结论 + 未检查层的遗留问题写入"风险说明"，随反思报告一并输出 |

### 边缘情况处理

| 场景 | 处理方式 |
|------|---------|
| 同一轮次中 L0 多次命中 | 每次命中均不计入失败轮次，但若连续命中 ≥3 次，应标记为"模式异常"触发 L0 起步的完整反思 |
| 反思过程中发现新的失败信号 | 如果新信号优先级更高，立即覆盖当前反思深度，从新信号对应的起始层级重新开始 |
| 无法确定信号类别 | 默认按"重复失败"处理，从当前失败轮次对应的层级起步 |
| 反思后仍需升级但无可用 ensemble | 输出反思报告，向用户说明"无法自修复，建议手动介入或升级审查" |

## 示例：反思报告（简略版）

以下为一次典型反思过程的简略示例，展示各层自检的证据填写方式。

```markdown
## 反思报告

### 触发信息
- **触发信号**：重复失败
- **当前失败轮次**：第 2 次
- **执行层级范围**：L0 → L1
- **原始任务摘要**：修复 `src/utils/format.ts` 中的日期格式化函数导致测试失败

### L0 操作层

| 检查项 | 结论 | 证据 |
|--------|------|------|
| L0.1 文件目标 | 是 | 两次修改均指向 `src/utils/format.ts`，路径正确 |
| L0.2 语法与格式 | 是 | `npm run typecheck` 通过，无语法错误 |
| L0.3 工具使用 | 是 | `edit` 工具替换成功，无错误返回 |
| L0.4 环境问题 | 是 | `npm test` 在未修改前可正常运行（12 passed） |

**L0 结论**：无问题

### L1 诊断层

| 检查项 | 结论 | 证据 |
|--------|------|------|
| L1.1 问题类型判断 | 否 | 原始诊断认为是"数据"类问题（格式输出值错误），但实际测试失败日志显示 `addDays` 函数被调用时传入了 `null` 而非日期对象。对照 `core.md` 诊断表，这属于"数据"类中的**参数/输入**问题，但根因不在格式化函数内部，而在调用方未做空值防护 |
| L1.2 排查链路方向 | 否 | 按照"数据"类的排查链路"输入/参数→数据源→解析/映射→…"，应先检查上游调用方传入的参数。当前修复在 `format.ts` 内部加 `if (date === null)` 防御，属于跳过上游直接修下游 |
| L1.3 混淆类别排除 | 是 | 无混淆——测试失败信息明确指向数据值异常，非网络/状态/交互类 |
| L1.4 治标还是治本 | 否 | 当前修复在 `format.ts` 中加了 null 防御，属于治标。根因是调用方 `ProfilePage.tsx` 在用户未设置生日时传入了 `null`，正确的修复应在上游调用方做空值判断（展示"未设置"或跳过格式化） |

**L1 结论**：发现 L1.1（问题类型子类判断错误）和 L1.2（跳过上游直接修下游）。应调整诊断：根因在 `ProfilePage.tsx` 调用方未处理空值，需撤消 `format.ts` 的防御性修改，改在 `ProfilePage.tsx` 调用前做空值判断。
```
