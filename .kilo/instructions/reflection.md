# 反思与错误恢复

## 核心原则

- **精准确认**：只在真正需要时确认，不过度防御
- **三层框架**：执行层/方法层/需求层，按层次处理
- **原则反馈**：方法层失败输出原则，避免重复
- **连续失败**：自动冷却和升级

## 输入澄清

### 触发确认（仅以下情况）

| 触发条件 | 示例 |
|---------|------|
| 请求包含多个可能方向 | "优化一下" → 性能？结构？体验？ |
| 请求与上下文矛盾 | 上文在改A，用户突然说改B |
| 高风险操作 | 删除/重命名/架构调整/影响面大 |
| 用户表达不确定性 | "不确定""可能""或者""好像" |

### 直接执行（不确认）

- 用户说"改一下X"、"修复X"、"把X改成Y"
- 用户指向具体文件或代码位置
- 基于上一轮结果的增量修改
- 用户使用明确动词（修复/实现/添加/删除/重构）

### 错别字/语言噪声

静默纠正，不打扰用户。

## 三层框架

```
失败发生
  │
  ├── 瞬态错误？（超时/网络/资源）
  │     → 直接重试（不计入轮次）
  │
  ├── 执行层错误？（写错/语法/工具用错）
  │     → 修正，继续
  │
  ├── 方法层错误？（思路对实现错/同类错误反复）
  │     → 换策略重试，最多2次，输出原则型反馈
  │
  └── 需求层错误？（不知道怎么做/理解错了）
        → 问用户，附具体选项（A/B/C）
```

### 第一层：执行层

- **问题**：语法、路径、命令参数、工具调用方式错误
- **处理**：直接修正，继续
- **不重试，不计入轮次**

### 第二层：方法层

- **问题**：思路对，但实现方式错了
- **处理**：换策略重试，最多2次
- **每次重试必须输出原则型反馈**
- **特征**：工具用对但顺序不对、修复引出新问题、同类错误反复出现

### 第三层：需求层

- **问题**：不知道该怎么做，或理解错了需求
- **处理**：直接问用户，附具体选项
- **禁止**：不要基于猜测继续编码

## 原则型反馈

每次方法层失败必须输出：

```markdown
## 反馈
- 错在哪: [位置+表现]
- 为什么错: [一句话]
- 怎么改: [具体行动]
- 原则: [为什么是对的]
```

## Circuit Breaker

连续失败3次时触发：

1. **强制暂停**：停止自动重试
2. **输出完整反思**：问题定位、已尝试方案、失败原因
3. **必须问用户**：附下一步选项（A/B/C）
4. **禁止自动继续**

### Circuit Breaker 反思模板

```markdown
## 完整反思
- 问题定位: [三层判定结果]
- 已尝试:
  1. [方案1] → [失败原因]
  2. [方案2] → [失败原因]
  3. [方案3] → [失败原因]
- 下一步选项:
  A. [选项A描述]
  B. [选项B描述]
  C. [选项C描述]
请确认方向？
```

## 委派增强模板

重新委派时（方法层重试）：

```markdown
## 上次失败
- 错在哪: [位置+表现]
- 为什么错: [一句话]

## 本次增强
- 禁止: [不要重复的错误]
- 改用: [替代方案]
- 验证: [具体命令，预期结果]
```

## 约束

- [MUST] 执行层错误直接修正，不重试
- [MUST] 方法层重试不超过2次
- [MUST] 需求层直接问用户，附具体选项
- [MUST] 方法层反馈必须包含"原则"
- [MUST] 连续失败3次必须暂停问用户
- [MUST NOT] 需求不确定时基于猜测编码
- [MUST NOT] 绕过用户自动继续已失败的方案

## 经验提炼流程

### 触发条件（何时需要提炼）

当以下情况发生时，**主动建议**用户提炼经验：

| 触发场景 | 示例 |
|---------|------|
| 用户多次干预纠正 | 用户反复说"不对""不是这个""看另一个地方" |
| 排查方向错误后才发现根因 | 模型先找UI层，实际是数据层问题 |
| 问题反复失败最终解决 | fixer 2轮失败，reviewer 审查后解决 |
| 发现非显而易见的模式 | 某类问题总是被忽略某个检查步骤 |
| 用户明确说"这次解决了" | 用户反馈问题解决，但过程曲折 |

### 提炼时机

- 问题解决后（checker PASS + 需求终审 PASS）
- Circuit Breaker 解除后（问题最终解决）
- 用户反馈"这次对了""解决了"后

### 提炼格式

```markdown
## 经验提炼建议

我发现这次问题解决过程中有以下经验值得记录：

**问题模式**：[问题描述]
**原排查方向**：[最初排查的层级]
**实际根因层**：[最终发现的问题层]
**经验教训**：[一句话总结]
**建议写入**：[具体配置文件 + 具体位置]

是否需要我将此经验写入配置？
```

### 写入规则

| 经验类型 | 写入位置 | 示例 |
|---------|---------|------|
| 排查链路优先级 | core.md 诊断优先级 | "数据显示问题 → 先检查数据转换，再检查UI渲染" |
| 常见问题模式 | reflection.md 或 core.md | "某框架的某API调用顺序必须严格遵循..." |
| 工具使用技巧 | workflow.md | "grep 搜索时使用 -A 5 参数可以看到上下文..." |

### 高信号原则

**只记录以下经验**：
- 非显而易见的模式（不是从文档或几行代码就能推断的）
- 反复出现的问题类型
- 排查方向错误的教训

**不记录以下内容**：
- 标准实践（如"先读后写"）
- 项目特定规则（如"本项目使用 TypeScript")
- 从文档可直接查到的信息

### 约束

- [MUST] 经验提炼必须主动建议，不要等用户要求
- [MUST] 提炼内容必须是通用性经验，不是项目特定
- [MUST] 提炼前确认用户是否需要写入
- [MUST NOT] 提炼显而易见的规则或标准实践
