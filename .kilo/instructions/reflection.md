# 反思与错误恢复

## 核心原则

- 具体反馈 > 抽象分类
- 过程推理 > 失败后反思
- 直接确认 > 猜测需求
- Self-Refine 精神：反馈必须具体、可操作。不是"错了"，而是"哪里错、为什么错、怎么改"
- ReAct 精神：推理和行动交替。不只是失败后反思，而是在过程中持续推理

## 三层框架

### 执行层（Execution）

**问题**：动手写错了（文件路径、语法、命令参数）

**处理**：直接修正，不重试，不计轮次

**反馈格式**：
```
错了哪里 → 怎么改
```

### 方法层（Method）

**问题**：思路对，但实现方式错了

**处理**：提取具体反馈，换策略重试（最多2次）

**反馈格式**：
```
错在哪 → 为什么错 → 换什么做
```

### 需求层（Requirement）

**问题**：不知道该怎么做，或理解错了需求

**处理**：直接问用户，不要猜

**问法**：具体指出不确定的地方，让用户确认

## 触发判断

```
失败发生
  │
  ├── 是执行层错误吗？
  │     特征：语法错误、路径写错、命令参数错、工具用错
  │     → 直接修正，不重试
  │
  ├── 是方法层错误吗？
  │     特征：思路合理但实现不对、修复引出新问题、同类问题反复
  │     → 提取反馈，换策略重试（最多2次）
  │
  └── 是需求层错误吗？
        特征：不知道该怎么做、需求有歧义、用户反馈与预期不符
        → 直接问用户，不要继续猜
```

## 具体反馈格式

### 反馈模板

每次失败必须输出：

```markdown
## 反馈

### 错在哪
[具体位置：文件:行号，或具体的错误表现]

### 为什么错
[我的理解 vs 实际原因，一句话说清楚]

### 怎么改
[明确的行动，不是"改进"而是"具体改什么"]
```

### 方法层重试增强

每次方法层重试时，必须在委派中包含：

```markdown
## 上次失败
- 错在哪: [feedback.错在哪]
- 为什么错: [feedback.为什么错]

## 本次增强
- 禁止: [上次犯的错误，明确列出]
- 改用: [替代方案，简短描述]
- 验证: [具体命令，预期结果]
```

## ReAct 式推理追踪

在修复过程中，保持推理轨迹：

```markdown
## 推理链

→ 我打算做什么：[行动]
→ 预期结果：[结果]
→ 实际结果：[结果]
→ 判断：[对了/错了/不确定]

[不确定时立即触发方法层反思，不等失败]
```

## 需求确认触发

**直接问用户，不要猜：**

| 触发情况 | 问法 |
|---------|------|
| 不知道该怎么做 | "这个功能有两个可能的方向：A还是B？" |
| 需求有歧义 | "你说的X，我理解是Y，你确认是这意思吗？" |
| 用户说"不太对" | "你说的'不太对'具体是指哪个文件的哪个行为？" |
| 修复后结果与预期不符 | "我修复后的预期是Y，但你觉得Z不对，哪里不对？" |

## 与 core.md 诊断优先级的衔接

方法层反思时，引用 core.md 的诊断链路：

```
我怀疑这个问题是[类别]类
按 core.md 的排查链路，应该先检查[链路第一步]
但实际上[实际发现]
所以真正的问题是[重新定位]
```

## 记忆机制

保留 `.kilo/learned/reflection_memory.md`。

### 写入时机

每次方法层错误后，将反馈精华写入记忆库：

```markdown
## 问题模式
- 类型: [数据/UI/交互/网络/状态/性能]
- 错在哪: [一句话]
- 为什么错: [一句话]
- 怎么改: [一句话]

## 下次注意
[同类问题的通用约束]
```

### 检索方式

遇到问题时，优先检索记忆库：
- 按类型匹配
- 按"错在哪"关键词匹配
- 命中共性模式时，应用记忆约束

## 约束

- [MUST] 执行层错误直接修正，不重试
- [MUST] 方法层重试不超过2次，超限则触发需求层
- [MUST] 需求层不确定时直接问用户，不继续猜
- [MUST] 每次失败输出具体反馈（错在哪/为什么/怎么改）
- [MUST] 方法层重试必须包含上次失败反馈
- [PREFER] 过程推理优于失败后反思
- [MUST NOT] 需求层问题用猜测代替确认
- [MUST NOT] 记忆库写入代替即时反馈
