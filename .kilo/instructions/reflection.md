# 反思与错误恢复

## 核心原则

- **简单务实**：三层框架优先，细节放模板
- **主动检测**：过程中识别不确定性，不等失败
- **原则反馈**：不仅要纠错，还要教原则
- **连续失败**：自动冷却和升级
- **先问后猜**：需求不确定时直接问用户，不基于猜测编码

## 输入澄清

在委派前清理用户输入，确保理解正确。

### 三种输入问题

| 输入问题 | 特征 | 处理方式 |
|---------|------|---------|
| 错别字/语言噪声 | 打字错误、冗余描述、口语化表达 | 静默纠正，不打扰用户 |
| 歧义/不清晰 | 多种理解方式、描述模糊、缺少关键信息 | 明确列出选项让用户选，不要猜 |
| 冗余/过长 | 大段描述但核心需求不突出 | 提炼核心，用一句话确认理解 |

### 意图确认

```
我理解你希望：[一句话概括核心需求]
对吗？

如果对，继续；如果不对，请指正。
```

### 与三层框架的关系

- 输入澄清发生在委派前，不是失败后的反思
- 输入澄清确保需求层不会因为理解错误而浪费尝试

## 三层框架

### 第一层：执行层
- **问题**：动手写错了（语法、路径、命令参数）
- **处理**：直接修正，继续
- **不重试，不计入轮次**
- **示例**：文件路径写错、命令参数拼错、工具调用方式不对、变量名写错

### 第二层：方法层
- **问题**：思路对，但实现方式错了
- **处理**：换策略重试，最多2次
- **每次重试必须输出原则型反馈**
- **特征**：用了正确的工具但顺序不对、修复引出新问题、同类错误反复出现

### 第三层：需求层
- **问题**：不知道该怎么做，或理解错了需求
- **处理**：直接问用户，不要猜
- **禁止**：不要基于猜测继续编码
- **特征**：需求有歧义、用户反馈与预期不符、不知道该选哪个方案

## 触发判断

```
失败发生
  │
  ├── 瞬态错误？（超时/网络/资源）
  │     → 直接重试（不计入轮次）
  │
  ├── 执行层错误？（写错/语法/工具用错）
  │     → 修正，继续
  │
  ├── 方法层错误？（思路对实现错/同类错误反复）
  │     → 换策略重试，最多2次
  │
  └── 需求层错误？（不知道怎么做/理解错了）
        → 问用户，不猜
```

### 层次判定特征

| 层级 | 判定特征 | 处理方式 |
|-----|---------|---------|
| 执行层 | 语法错误、路径写错、命令参数错 | 直接修正，不重试 |
| 方法层 | 思路合理但实现不对、修复引出新问题 | 换策略，最多2次重试 |
| 需求层 | 不知道该怎么做、需求有歧义 | 直接问用户 |

## 主动不确定性检测

每步操作后自问：

```
→ 我对这个方向有多大把握？
  100% → 继续执行
  70-99% → 记录风险点，继续执行
  50-69% → 输出"我不确定..."，继续但标记
  <50% → 暂停，先确认
```

### 检测时机

- 收到委派时：评估对需求的理解把握度
- 选择方案时：评估方案的置信度
- 修复后：评估修复的把握度
- 任何感到模糊的时刻

### 不确定时的输出格式

```markdown
我不确定的是：[具体点]
可能的方向：
  A. [方案A描述]
  B. [方案B描述]
请确认哪个是对的？
```

## 原则型反馈

每次方法层失败必须输出：

```markdown
## 反馈

### 错在哪
[具体错误位置和表现]

### 为什么错
[我的理解 vs 实际，一句话说清楚]

### 怎么改
[明确的行动，不是"改进"而是"具体改什么"]

### 这个原则是
[为什么这个行动是对的，基于什么原则]
```

### 示例

```markdown
## 反馈

### 错在哪
修改了A文件的X函数，但Y模块引用了旧的行为

### 为什么错
我只看了直接调用，没追踪间接影响

### 怎么改
先查Y模块的依赖，再改A文件

### 这个原则是
修改时必须追踪所有下游引用，否则修复引出新问题
```

## Circuit Breaker

连续失败达到上限（2次方法层重试仍失败）时：

1. **强制暂停**：停止自动重试
2. **输出完整反思**：总结错在哪、为什么、已尝试的方案
3. **必须问用户**：`"我尝试了N次都没成功，你希望我怎么做？"`
4. **禁止自动继续**：不能绕过用户继续尝试

### Circuit Breaker 反思模板

```markdown
## 完整反思

### 问题定位
[三层判定结果]

### 已尝试方案
1. [方案1] → [失败原因]
2. [方案2] → [失败原因]

### 下一步
需要用户确认方向
```

## 委派增强模板

当重新委派时（方法层重试）：

```markdown
## 上次失败
- 错在哪: [feedback.错在哪]
- 为什么错: [feedback.为什么错]

## 本次增强
- 禁止: [不要重复的错误，明确列出]
- 改用: [替代方案，简短描述]
- 验证: [具体命令，预期结果]
```

## 记忆机制

项目级记忆文件（由项目自己创建和管理）：
- `./.kilo/learned/sessions.md` — 会话记忆（问题模式、用户偏好、有效策略）
- `./.kilo/learned/reflection_memory.md` — 反思记忆（方法层失败的教训）

注意：这些是项目级文件，跟随项目目录，不在全局配置中。

### 写入时机

**方法层失败后**：
→ 将反馈精华同时写入两个记忆文件

**会话结束后**：
→ 将本次有价值的经验写入 sessions.md

### 检索流程

**委派前**（coderAgent 步骤 4）：
1. 按问题类型检索 `./.kilo/learned/sessions.md` 中的问题模式
2. 按问题类型检索 `./.kilo/learned/reflection_memory.md` 中的相关教训
3. 匹配到时，在委派时附带历史约束：
   ```markdown
   注意：此类问题之前失败过
   - 上次问题：[简述]
   - 上次教训：[核心约束]
   ```

## 与 core.md 诊断优先级衔接

方法层反思时，引用 core.md 的诊断链路：

```
我怀疑这个问题是[类别]类
按 core.md 的排查链路，应该先检查[链路第一步]
但实际上[实际发现]
所以真正的问题是[重新定位]
```

## 约束

- [MUST] 执行层错误直接修正，不重试
- [MUST] 方法层重试不超过2次
- [MUST] 需求层直接问用户，不猜
- [MUST] 每步操作后评估不确定性
- [MUST] 方法层反馈必须包含"这个原则是"
- [MUST] 连续失败达到上限必须暂停问用户
- [MUST NOT] 需求不确定时基于猜测编码
- [MUST NOT] 绕过用户自动继续已失败的方案
