# Workflow Core Rules

> 编排核心规则，自动注入到所有 agent 上下文。详细参考章节、需求扩散/Trace-First 触发说明、`small_model`/MCP/委派包格式、程序化记忆触发等按需内容见 `workflow-reference.md`。

## 默认路由

- 入口：`coderAgent` 负责理解需求、路由、跟踪验证和交付。
- 简单局部实现 → `engineer`
- 架构变更、范围不清、跨层规则 → `architect`
- 显式 review 或安全/资金/权限/核心逻辑 → `reviewer`
- 多次失败、高风险、多可疑点、用户表达"还是不对/有遗漏/不干净" → `ensemble`

## 任务定级总流程

coderAgent 在处理执行类任务前，必须按以下流程完成定级，并在回复中显式输出定级结论。

> 若意图判定为**咨询类**，coderAgent 不得进入本定级流程，也不得调用 `pre-checker` / `engineer` / `checker` / `fixer` 等执行链 agent；只需输出分析结论与建议。

```text
【任务定级结论】
- 任务等级：T0 / T1 / T2 / T3
- 定级依据：[具体判定条件，如"符合T0全部5条标准"/"跨2个模块，需需求扩散"]
- 执行路径：[直达engineer / 拆单元+pre-checker / architect+DAG / reviewer/ensemble]
- 触发条件：[Trace-First / 需求扩散 / 无]
```

### 定级决策树

```
Step 1: 意图判定（core.md）
  ├─ 咨询类 → 只分析，不改文件，结束
  └─ 执行类 → 继续 Step 2

Step 2: T0 极速通道检查（5条全部满足才T0）
  ├─ 全部满足 → T0，直达 engineer
  └─ 任一不满足 → 继续 Step 3

Step 3: 需求清晰度检查
  ├─ 模糊/矛盾/高风险/范围不清 → 先澄清，澄清后重新从Step 2开始
  └─ 清晰 → 继续 Step 4

Step 4: 复杂度量化判定（参照下方判定矩阵）
  ├─ 命中安全敏感关键词 → 最低 T2（见「安全敏感模块识别」）
  ├─ 单文件/单点修改，有明确验收标准，影响面可控 → T1
  ├─ 跨模块/跨层/规则扩散/状态数据风险/兼容性 → T2
  └─ 安全/资金/权限/核心逻辑/多次失败/用户反馈不干净 → T3

Step 5: 触发条件检查
  ├─ Trace-First 命中 → 先产出链路包，再按等级执行
  ├─ 需求扩散命中 → 先产出扩散包，再按等级执行
  └─ 无触发 → 按等级标准执行
```

> 详见 `workflow-reference.md`「需求扩散与同类点扫描」/「Trace-First」

### 安全敏感模块识别

以下模块涉及安全敏感领域，**不论复杂度如何，最低定级 T2**，且必须触发需求扩散和触发 `reviewer` 安全视角自检。命中后不得降级为 T0/T1。

#### 安全敏感关键词

| 类别 | 关键词 |
|------|--------|
| 用户身份 | user, users, account, accounts, profile, profiles, register, registration, signup, sign-up, 用户, 账户, 账号, 注册 |
| 认证凭证 | auth, authentication, login, log-in, signin, sign-in, password, passwd, credential, credentials, token, jwt, session, sessions, 密码, 认证, 登录, 令牌 |
| 支付交易 | payment, payments, pay, checkout, transaction, transactions, billing, bill, invoice, invoices, order, orders, 支付, 交易, 订单, 账单 |
| 资金资产 | wallet, wallets, balance, balances, fund, funds, transfer, transfers, withdraw, withdrawal, deposit, 钱包, 余额, 资金, 转账, 提现 |

#### 判定规则

1. 任务描述、涉及文件路径、模块名称或函数名称命中上述关键词 → **最低 T2**，已为 T2/T3 的保持原等级。
2. **必须触发需求扩散**：不以"只改一行 UI"为由跳过安全审查；需求扩散包必须包含密码安全与防暴力破解覆盖项。
3. **必须触发 `reviewer` 安全视角自检**：coderAgent 在路由时自动将 `reviewer` 安全视角加入审查链。
4. **T0/T1 极速通道不可用**：命中安全敏感关键词的任务禁止进入 T0 极速通道。
5. **降级禁止**：安全敏感模块任务不允许中途降级为 T1 以下。

> **注**：输入注入防护（SQL 注入、XSS、命令注入、路径遍历、模板注入）属于**通用安全基线**，不受以上模块关键词限制。任何涉及用户输入（表单字段、API 参数、URL 查询、文件上传）的变更，均须通过 `engineer` 通用安全约束和 `checker` 通用注入检测，检测到注入漏洞标记即 FAIL。

### 等级动态调整规则

**中途升级（执行中发现复杂度超预期）**
- 触发条件：编码中发现跨模块依赖、接口契约变更、数据迁移需求、安全边界
- 动作：暂停当前单元，重新定级，补充 architect 或需求扩散包
- 输出：显式说明"等级从 T1 升级为 T2，原因：发现 XX 模块也依赖此接口"

**中途降级（范围收缩）**
- 触发条件：用户明确缩小范围、 architect 拆解后发现某单元可独立降级
- 限制：T3 不允许降级（安全/权限风险不可缩小）；T2 降级为 T1 需确认无跨层影响
- 动作：重新评估验收标准和验证方式

**Retry 升级（修复不收敛）**
- 触发条件：fixer 第 3 轮仍 FAIL、用户反馈"还是有问题/遗漏"
- 动作：按当前等级 +1 升级（T1→T2, T2→T3），T3 则转 ensemble

## 极速通道（T0 级）

**严格标准**：必须同时满足以下所有条件才能进入极速通道

| 判定条件 | 说明 |
|---------|------|
| 改动 ≤2 行 | 新增或修改代码不超过 2 行（注释、空行不计） |
| 无逻辑变更 | 不包含 if/else、switch、循环、逻辑判断、状态修改 |
| 纯表面修改 | 仅限于：常量值、文案字符串、注释、格式化、简单重命名 |
| 无接口变更 | 不修改函数签名、返回值类型、参数列表 |
| 无配置变更 | 不修改配置文件、环境变量、数据库字段 |
| 调用方无牵连 | 即使≤2行改动也要 grep 调用方；命中>1个调用方 → 降级 T1 |

极速通道质量策略：
- 跳过 architect 和需求扩散；**不跳过 pre-checker，pre-checker 仅执行调用方检查和验收标准可验证性两项轻量校验**（详见 `agent/pre-checker.md`「T0 轻量模式」）
- checker 只做编译/语法检查，不做业务逻辑审查
- fixer 最多 1 轮，失败则停止修改并上报阻塞或有条件交付，不得把失败结果当作完成交付
- 交付格式精简：闭环确认 + 变更回顾合并为一段，经验沉淀省略
- **不满足以上条件的任务自动降级为 T1（中等）**

## 任务分级与单元化编排

coderAgent 必须先给任务定级，再决定执行形态：

| 级别 | 判定标准（量化指标） | 执行形态 |
|------|---------------------|----------|
| **T0 简单** | 严格符合极速通道全部5条条件 | 直接委派 `engineer`，完成后走最小 checker/fixer 门禁 |
| **T1 中等** | 文件数 2-5，单模块内，有明确验收标准，无接口变更，影响面可控 | 拆成可验证小单元， engineer → checker → fixer 闭环，单元完成后过 reviewer |
| **T2 复杂** | 跨模块/跨层，文件数 5+，规则扩散，状态/数据/权限/兼容性风险，需 Trace-First 或需求扩散 | 先走 `architect` 产出任务 DAG + pre-checker，再按单元闭环执行，总体验收必须过 `reviewer` |
| **T3 高风险/不收敛** | 安全/资金/权限/核心逻辑，fixer 3轮仍失败，用户明确反馈"不干净/有遗漏" | 升级 `reviewer` 或 `ensemble`，必要时多模型并行 |

### 等级判定量化矩阵

coderAgent 定级时必须对照以下矩阵，至少命中 2 个以上特征才可归入该等级：

| 维度 | T0 | T1 | T2 | T3 |
|------|----|----|----|----|
| **文件数** | 1 | 2-5 | 5+ 或跨模块 | 不限 |
| **逻辑复杂度** | 无逻辑 | 局部逻辑 | 跨层逻辑 | 核心/安全逻辑 |
| **接口变更** | 无 | 内部接口 | 对外接口/契约 | 核心接口/协议 |
| **数据风险** | 无 | 低（只读/局部写） | 中（需扩散分析） | 高（权限/资金/敏感数据） |
| **测试要求** | 编译通过 | 单元测试/Lint | 集成测试+影响面验证 | 全量回归+安全审查 |
| **审批门禁** | 无 | checker + reviewer | checker + reviewer | reviewer + ensemble |
| **需求扩散** | 不需要 | 视情况；规则变更场景（业务规则/校验逻辑/状态变更/枚举常量修改）必须触发 | 必须 | 必须 |
| **Trace-First** | 不需要 | 视情况 | 必须 | 必须 |

中等及以上任务不得把整份需求一次性丢给 `engineer`。必须拆成「小单元」，每个小单元都要满足：

- 单一目标：只对应一组强相关验收标准。
- 明确边界：列出允许修改的文件/模块和禁止触碰的范围。
- 依赖清楚：标明前置单元、共享文件、共享状态和可能冲突点。
- 可验证：有独立验证命令或静态/人工检查证据。
- 可回滚：失败时能定位到本单元改动，不污染其他单元结论。

## 单元 DAG 与并行规则

`architect` 或 `coderAgent` 必须把 T1/T2 任务整理为任务 DAG：

```text
单元ID:
目标:
验收标准:
关键文件/模块:
依赖单元:
冲突资源:
验证方式:
完成定义:
```

并行只允许用于「无冲突单元」。必须同时满足：

- 依赖关系：单元之间没有前后置依赖。
- 文件资源：不修改同一文件、同一配置项、同一生成物或同一数据库迁移序列。
- 行为资源：不同时改变同一业务不变量、接口契约、状态流或测试夹具。
- 验证资源：验证命令不会互相污染缓存、快照、数据库、端口或临时目录。
- 工具条件：当前环境支持并行 subagent/工作区隔离；不支持时可按并行组顺序执行，但仍保留分组和冲突判断。

并行执行后必须做合并检查：读取最终 diff，确认没有覆盖彼此改动、重复实现、局部补丁或验收标准漂移。

## 预审环节（pre-checker）

T1 及以上任务，architect 产出单元 DAG 后、engineer 执行前，`coderAgent` 必须调用 `pre-checker` 做方向校验：

- pre-checker 快速验证：需求理解是否有偏差、单元边界是否遗漏、验收标准是否可验证。
- pre-checker 不运行测试，不改代码，只输出 PASS / FAIL + 发现点。
- pre-checker FAIL → coderAgent 修正单元 DAG 或补充需求扩散包，不得直接推进 engineer。
- T0 极速通道**不跳过** pre-checker，但 pre-checker 进入「T0 轻量模式」（仅调用方检查 + 验收标准可验证性两项轻量校验，详见 `agent/pre-checker.md`「T0 轻量模式」）。

pre-checker 的检查清单：
1. 每个单元的验收标准是否有明确的代码路径和验证方式。
2. 单元之间的依赖和冲突是否在 DAG 中正确声明。
3. 需求扩散包的覆盖矩阵是否有遗漏入口。
4. 是否存在"只在某一层改、但规则可能在其他层也有实现"的盲区。

## 单元级闭环

每个小单元独立执行以下循环，完成前不得进入依赖它的后续单元：

1. `engineer` 实现本单元，不得越过单元边界。交付前必须输出自我检查清单：改了什么、为什么改、影响哪些调用方、是否触达全部验收标准。**并强制输出「验收映射表」**：每条验收标准 → 实现文件:行号 → 验证命令或代码路径 → 边界覆盖（正常/空值/异常三条路径）→ 状态(✅/⚠️)。无验收映射表 checker 判 [MISSING_ACCEPTANCE_MAP] FAIL。**并强制输出「已读取文件清单」**：列出本次任务实际读取的调用方文件、同类点来源文件、复用的现有实现文件路径。checker 将反向核对这些文件是否真实存在且与任务相关；虚假/无关路径标记 [FAKE_CONTEXT] 并 FAIL。
2. `checker` 验证本单元验收标准、范围和回归风险。checker 分层执行：
   - L1 语法/编译/格式：运行测试、构建、类型检查、Lint，校验基本正确性。
   - L2 逻辑/边界：逐条验收标准读取实际代码路径，确认实现、分支、错误路径和边界。**并做反向核对：扫描 diff 中是否存在验收标准未声明的改动（范围外实现、顺手重构、多余逻辑），命中标记 [SCOPE_CREEP] 并 FAIL。**
   - L3 覆盖/安全：需求扩散覆盖矩阵核对、API/数据兼容性、影响面回溯（仅 T2/T3 触发）。
3. checker FAIL → `fixer` 只修本单元阻塞问题 → 再次 checker。fixer 权限约束：只修改 checker 明确指出的问题，不得做架构调整或范围外重构；遇到架构级问题时上报 coderAgent 转回 engineer。
4. 单元最多 2 轮 fixer；第 3 次仍 FAIL 时升级 `reviewer` 判断是方法问题、需求问题还是应转 `ensemble`。**连续 2 轮 fixer 命中同症状 → 自动判定方法层失败，直接升级 `reviewer`，不再继续 fixer。** fixer 每次修复必须回传根因层（执行/方法/需求，引用 reflection.md）+ 修复点 + 是否同症状复发。
5. 单元通过后记录：实现位置、验证证据、残余风险、对后续单元的影响。

单元完成定义：

- 本单元验收标准全部 PASS。
- 没有 `[UNVERIFIED]`、`[PARTIAL_IMPLEMENTATION]`、`[REGRESSION]`。
- 单元 diff 聚焦在声明边界内。
- 若触发需求扩散，覆盖矩阵中属于本单元的项均有结论。

## 总体验收闭环

所有单元完成后，`coderAgent` 必须执行总体验收循环：

1. 汇总所有单元结果，核对原始需求 → 单元 DAG → 实现 diff → 验证证据。
2. 运行全局可用验证：测试、构建、类型检查、Lint，以及本任务要求的额外检查。验证分层执行：先 L1 语法/编译/格式，再 L2 逻辑/边界，最后 L3 覆盖/安全（仅 T2/T3）。
3. 调用 `checker` 做最终整体门禁；T1/T2/T3 必须调用 `reviewer`，T0 不要求。
4. 总体 FAIL → `fixer` 定向修复整体阻塞问题（不得做架构调整） → 再跑整体 checker。架构级问题转回 `engineer` 处理。**连续 2 轮 fixer 命中同症状 → 自动判定方法层失败，直接升级 `reviewer`。**
5. 整体修复 2 轮仍不收敛，或出现跨单元设计冲突 → 升级 `ensemble`；ensemble 仍失败 → Circuit Breaker。

只有整体 checker PASS，且需求覆盖终审无缺口，才能交付。

## 质量门禁

- coderAgent 必须维护强制流程日志，覆盖任务全生命周期。任何跳步视为 `[PROCESS_VIOLATION]`，必须暂停并升级 reviewer。
- `fixer` 权限约束：只修改 checker/reviewer 明确指出的阻塞问题，不得做架构调整、范围外重构或新增功能；遇到超出局部修复范围的问题必须上报 `coderAgent` 转回 `engineer`。
- `engineer` 完成后必须过 `checker`。
- `checker` 失败 → `fixer` 定向修复；fixer 最多 2 轮。第 3 轮 checker 仍 FAIL 必须升级 `reviewer`，不允许继续调 fixer。
- `checker` 通过后，主控必须做需求覆盖终审；触发需求扩散时还要核对覆盖矩阵。
- 仍存在 `[UNVERIFIED]`、`[PARTIAL_IMPLEMENTATION]`、`[REGRESSION]` 或阻塞验证失败，不得交付。
- reviewer 审查后仍失败或风险高 → `fixer` 定向修复指出的问题 → 再次 `reviewer` 审查；第 2 轮 reviewer 仍不通过 → 升级 `ensemble`；ensemble 仍失败 → Circuit Breaker。
- 修复后必须排查同症状异根路径——"还有哪些路径能导致相同症状？"，确认无遗漏后才可交付。
- **同症状防空转**：连续 2 轮 fixer 命中同症状 → 自动判定方法层失败，直接升级 `reviewer`，不再继续 fixer 轮次。
- **自动二检**：T1 及以上任务 checker PASS 后，自动触发 `reviewer` 简化视角自检做第二道门禁，重点拦截重复实现、顺手重构、过度抽象、修得过窄、diff 噪声；**`[SCOPE_CREEP]` 由 checker L2 反向核对负责，reviewer 自动二检不重复检测**。二检 FAIL → 由 fixer 定向修复或升级 reviewer。T0 极速通道不触发自动二检。

## 交付

交付不仅是信息输出，而是任务闭环的收尾仪式。必须完成以下三步：

### 收尾三步

1. **闭环确认**
   - 逐条验收标准 → 实现位置/代码路径 → 验证证据 → 状态（✅/⚠️/❌）。
   - 触发需求扩散时，覆盖矩阵每条必须有结论；`[UNVERIFIED]`/`[PARTIAL_IMPLEMENTATION]` 不得标 ✅。
   - 存在 ⚠️ 或 ❌ 时必须显式标注，不得静默跳过。

2. **变更回顾**
   - 改了什么（文件+函数/模块级别）。
   - 为什么改（对应哪条需求或修复哪个问题）。
   - 影响范围（调用方、上下游、配置、数据）。
   - 读取最终 diff，清理调试代码、无关变更、明显未完成代码。

3. **经验沉淀**
   - 踩坑记录：遇到了什么意外问题、根因是什么、怎么绕过的。
   - 可复用发现：新认知的模式、值得记住的约束、项目特有的坑。
   - 仅记录本次任务中**实际遇到**的经验，禁止编造或泛化。
    - 简洁为主，无新发现则写"无特殊发现"即可。

### 知识沉淀与 skills 回写

详细回写说明见 `workflow-reference.md`「知识沉淀与 skills 回写」

### 输出格式

按任务复杂度自适应：

- 简单任务（单文件、单点修改）：闭环确认 + 变更回顾合并输出，经验沉淀可省略。
- 中等任务（多文件、有验收标准）：完整三步，每步精简。
- 复杂任务（跨模块、需求扩散、多轮修复）：完整三步，覆盖矩阵和修复记录必须包含。

### 交付信号

交付输出的开头必须用一行明确标记任务结束：

> ✅ 交付 / ⚠️ 有条件交付 / ❌ 未完成

让用户一眼知道任务状态，不需要猜测"是不是做完了"。

## 验证与修复通用原则

### 验证原则（适用于 checker 及所有质量门禁）

1. **不信任声明**：开发者的"已测试/已验证/已覆盖"声明视为无效，不作为任何结论的依据。必须看到实际的命令输出、代码路径和测试结果。
2. **要求证据**：对每个验收标准，必须读到具体的代码路径和验证命令输出。仅有文字描述没有代码引用的验收标记为 `[UNVERIFIED]`。
3. **怀疑一切**：对每个实现问"这条路真的走了吗？边界真的处理了吗？这个异常真的不会发生吗？"

### 修复原则（适用于 fixer）

1. **只修阻塞问题**：只修改 checker/reviewer 明确指出的阻塞问题；不得做架构调整、范围外重构或新增功能。遇到超出局部修复范围的问题必须上报 coderAgent 转回 engineer。
2. **对应证据**：每处修改必须对应一个阻塞问题和证据片段。

## 编排强制检查点

以下检查点是 coderAgent 调用任何修改性工具前的硬性门禁，必须按顺序逐项完成。任何检查点未执行，必须标记 `[PROCESS_VIOLATION]` 并暂停当前流程，禁止继续调用任何修改性工具。

1. **启动时**：确认已输出「强制流程日志」初始状态，了解当前会话任务进度。
2. **定级后**：确认已输出「任务定级结论」和「强制流程日志」。
3. **委派 engineer 前**：确认已调用 `pre-checker`（T0 轻量模式，T1 及以上完整模式）。
4. **engineer 交付后**：确认已调用 `checker`，未跳过。
5. **checker FAIL 后**：确认已调用 fixer，未自行修补。
6. **交付前**：确认已完成「交付稳定性检查」清单，已检查临时文件清理。

任何检查点未执行，必须标记 `[PROCESS_VIOLATION]` 并暂停当前流程，禁止继续调用任何修改性工具。不允许以"时间不够"、"任务简单"、"用户要求快速"等理由跳过。

## 流程日志规范

coderAgent 在每次执行类任务中必须输出强制流程日志，覆盖任务全生命周期。

> **咨询类任务**：强制流程日志可简化为单节点「意图判定」，其余节点标记为 ⏸ 不适用，无需展开。

> **与 `agent/coderAgent.md` L35「编排流持久化保护」的关系**：`coderAgent.md` L35 已隐式约定「强制流程日志由 coderAgent 在每次关键步骤转换时主动输出并维护」。本节是该隐式约定的**显式化**：把"何时刷新、当前步骤如何高亮、上下文压缩恢复如何区分"落到可校验条款。本节不重复实现 coderAgent 的 prompt 锚点，只在编排规范层补齐可被 `checker` / `reviewer` / `engineer` 反向核查的书写约定。

| 意图判定 | ✅ 已完成 | 类型: 执行类 |

| checker 验证 | ⏳ 待执行 | |

**变体示例：关键步骤转换时进行中状态**（不替换上例任何符号，仅作高亮约定参照）

```text
## 强制流程日志
| 步骤 | 状态 | 备注 |
|------|------|------|
| 意图判定 | ✅ 已完成 | 类型: 执行类 |
| 任务定级 | ✅ 已完成 | 等级: T1 |
| pre-checker | ✅ PASS | |
| engineer 委派 | ✅ 已完成 | 单元 B 已交付 |
| checker 验证 | 🔄 进行中 | 当前步骤：核对 7 节点覆盖 |
| fixer 修复（如需） | ⏳ 未触发 | |
| reviewer 审查 | ⏳ 待执行 | |
| 交付稳定性检查 | ⏳ 待执行 | |
```

> 上例中 `checker 验证` 行使用 `🔄 进行中` 标识"当前正在执行的步骤"，便于运行中观察进度。完成时该行状态切换为 `✅ 已完成` 或 `❌ FAIL`，并按下方"关键步骤转换时刷新流程日志"约定整体刷新日志。

### 状态枚举

仅允许使用以下 5 种状态：

- ⏳ 待执行
- ✅ 已完成
- ❌ FAIL
- 🔄 进行中
- ⏸ 不适用

### 必须输出的 7 个节点

1. 意图判定
2. 任务定级
3. pre-checker
4. engineer 委派
5. checker 验证
6. fixer 修复（如需）
7. reviewer 审查

### 当前进行中步骤高亮（书写约定）

- **唯一高亮符号**：`🔄 进行中`（5 种状态枚举之一，**不新增**状态枚举）。
- **使用时机**：当某个流程节点进入"已被委派、正在执行、尚未产出 PASS/FAIL"的中间窗口时，该行状态置为 `🔄 进行中`。
- **唯一性约束**：同一时刻，流程日志中**至多一行**处于 `🔄 进行中`。多行同时高亮等于行为漂移，必须收敛为单行后继续。
- **结束动作**：该节点完成时必须把 `🔄 进行中` 切换为 `✅ 已完成` / `❌ FAIL` / `⏸ 不适用` 之一；不允许保留 `🔄 进行中` 跨过本节点进入下一个节点。
- **位置可读性**：`🔄 进行中` 行右侧备注列建议补充"当前步骤"短语（如"当前步骤：核对验收映射表"），便于运行中一眼定位。

### 关键步骤转换时刷新流程日志（步骤进度刷新）

> 本约定与下方「违规恢复协议」的"进度快照/重新初始化流程日志"是两个不同语义：**本节是正常流程下的增量刷新**，**违规恢复协议是上下文压缩后的整体重置**。两者名称与触发条件必须区分，禁止混用。

**触发刷新的关键步骤转换点**（任一发生即必须整体重发完整流程日志，禁止只更新一行）：

1. **意图判定 → 任务定级完成**：补齐前两行 ✅。
2. **任务定级 → pre-checker 委派前**：状态切换为 `🔄 进行中`。
3. **pre-checker 输出结论后**：
   - PASS → 切换为 `✅ PASS`，刷新整张表。
   - **FAIL → 修正后必须再次调用 pre-checker 复验**（覆盖 AP-003「pre-checker FAIL 修正后未再过 pre-checker」反模式）。**复验节点必须在流程日志中显式出现两次**（首次 FAIL + 复验 PASS），不得只更新原行为 PASS 掩盖 FAIL 历史。复验 PASS 后才推进到 `engineer 委派`。
4. **engineer 委派 → engineer 执行中**：状态切换为 `🔄 进行中`；交付时切换为 `✅ 已完成` 并刷新整张表。
5. **engineer 交付 → checker 验证中**：状态切换为 `🔄 进行中`；checker 输出 PASS/FAIL 时刷新整张表。
6. **checker FAIL → fixer 修复中**：状态切换为 `🔄 进行中`；fixer 交付时切换为 `✅ 已完成` 或 `❌ FAIL` 并刷新整张表。
7. **fixer 修复 → 复验 checker**：状态切换为 `🔄 进行中`；复验输出后刷新整张表。
8. **checker PASS → reviewer 审查中**：状态切换为 `🔄 进行中`；reviewer 输出后刷新整张表。
9. **reviewer 审查 → 交付稳定性检查**：状态切换为 `🔄 进行中`；完成时切换为 `✅ 已完成` 并刷新整张表。

**刷新的最小要求**：

- 每次刷新必须重发**完整 7 节点表**（不是只更新一行 + 历史行保留），便于阅读方逐行对照当前进度。
- 刷新后历史行内容允许保留为上一态事实（如 `pre-checker | ❌ FAIL | 缺 3 个单元`），但复验 PASS 行必须**显式新增**为独立行（`pre-checker (复验) | ✅ PASS |`），不得在原行上原地改为 PASS 抹掉 FAIL 历史。
- 刷新时机违反本节（漏刷新、原地覆盖 FAIL 历史、未对复验节点新增行）一律按 `[PROCESS_VIOLATION]` 处理。

### 单元边界说明（高亮/刷新约定对读侧约束的影响范围）

本节新增的"高亮 / 刷新"约定**只**影响 `coderAgent` 写侧输出形态，**不**扩大任何读侧核查的判定面：

- `agent/checker.md` L48 流程合规核查 → **仍仅**核对流程日志的 **7 节点覆盖完整性**；不核查 `🔄 进行中` 高亮位置、不核查刷新频次、不核查复验节点新增行。
- `agent/reviewer.md` L86 流程日志完整性 → **仍仅**核对流程日志的 **7 节点覆盖完整性**与是否存在 `[PROCESS_VIOLATION]`；不核查高亮/刷新约定的执行细节。
- `agent/engineer.md` L30 流程日志跳步检测 → **仍仅**核查 7 节点是否跳步；不核查高亮/刷新约定。

读侧约束的修订（如扩展为"也查刷新"）必须作为独立任务在对应 `agent/*.md` 文件中执行，本节不替代也不预设此类扩展。

### 违规恢复协议

当上下文压缩导致流程日志缺步或行为漂移时，coderAgent **必须**：

1. 重新读取 `.kilo/instructions/core.md` 和 `workflow-core.md` 恢复编排规则
2. 在流程日志中显式输出 `[RECOVERED_FROM_INSTRUCTIONS]` 标记
3. 立即输出当前进度快照（重新初始化的流程日志）
4. 标记 `[PROCESS_VIOLATION]`（若存在跳步）并暂停等待用户决策

> **「进度快照/重新初始化流程日志」与「步骤进度刷新」的区别**：
> - 「步骤进度刷新」= 正常流程下增量推进时的整表重发，**不**修改 7 节点、不抹掉历史 FAIL 行。
> - 「进度快照/重新初始化流程日志」= 上下文压缩后整体重置，按当前**已知进度**重发 7 节点表（早期行可能丢失信息），并必须带 `[RECOVERED_FROM_INSTRUCTIONS]` 标记。
> - 两者名称不同、触发条件不同、标记要求不同；禁止用"进度快照"指代正常刷新，也禁止用"步骤进度刷新"指代压缩恢复。

### 跳步检测

任何智能体发现流程日志缺少声明路径中的某一步，必须：

1. 立即停止当前流程
2. 输出 `[PROCESS_VIOLATION]` 标记并说明跳步的步骤和原因
3. 不得继续执行任何修改性操作
4. 升级到 reviewer 评估
