# Workflow Rules

## 默认编排
入口为 `coderAgent`（理解需求→路由→跟踪→交付）。按复杂度路由：
- **简单**（实现/配置/文档/局部修复）→ `engineer`
- **中等/复杂**（架构变更、高风险、范围不确定）→ `architect`
- 显式 review 请求或涉及安全/资金/核心逻辑 → `reviewer`
- [MUST] 涉及调用链/数据流/状态流/配置流/根因不明或用户要求排查 → 先进入 `trace-first`

## Trace-First

### 触发条件
[MUST] 以下场景先 trace，未形成链路包前不直接修改：
- 数据异常、状态异常、交互失效、接口异常、性能异常
- 跨模块、多文件、链路长、配置影响明显
- 用户反馈"还是不对""有遗漏""链路有问题""先分析原因"

### 输出要求
- 问题类型、入口与目标行为、关键链路节点
- 每层输入/输出或状态变化
- 已确认异常点与待证伪假设
- 建议优先排查层和验证点
- 缺少复现条件时先补证据，不带着关键假设直接修改

## 何时升级到 Ensemble
满足任一条件升级 `ensemble`：
- 用户要求最高质量/并行模型/关键模块级把关
- 单模型修复循环反复无效，**且已完成反馈协议（方法层重试2次仍失败）**
- 高复杂度+高风险需多模型交叉验证
- 跨多层且高优先级排查层存在多个可疑点，单模型难以收敛
- 用户表达质疑/烦躁（"还是不对""改了很多次""深度分析""还有遗漏"），coderAgent **先触发反馈协议（按三层框架判断），若为需求层问题则澄清，若仍失败或为执行层/方法层持续失败，则升级**

[MUST] 任何升级到 ensemble 的决策必须附带最近一次反馈报告作为上下文，以便 ensemble 步骤1复用而非从零解析。

## 委派与上下文

### 委派模板（必须包含上下文锚定）

```text
Task @智能体:
- 任务来源: [新需求 | 第N轮修复 | 用户反馈"XXX"]
- 上下文锚定:
  - 上次目标: [一句话]（如有）
  - 上次状态: [成功/部分失败/全部失败]（如有）
  - 本次差异: [与上次的不同点]（如有）
- 目标: [一句话目标]
- 关键文件: [路径列表]
- 约束: [技术栈/范围/禁止事项]
- 验收标准: [每条标准附：文件/函数/验证方式]
- 已知失败: [命令 + 关键片段]（如有）
- 反馈报告: [上次具体反馈：错在哪/为什么/怎么改/原则]（升级或重试时必须附带）
```

### 委派规则
- [MUST] 只传递高信号信息：目标、关键文件、约束、验收标准、失败片段
- [MUST NOT] 转发完整对话、长日志和无关背景
- [PREFER] 项目级 `AGENTS.md` 和 `.kilo/skills/` 优先作为知识来源；全局规则做兜底
- 排查类任务额外传递：问题类型、已定位链路、上下游优先级、已排除/剩余可疑层

## 交付要求

### 分层交付

| 任务特征 | 输出层级 |
|---------|---------|
| 单文件、≤50行变更、无架构影响 | Tier 1 |
| 多文件、≤200行变更、需说明关联 | Tier 2 |
| 架构变更、跨模块、>200行、高风险 | Tier 3 |

**Tier 1（简单任务）**：
```
✓ 完成 | 变更：[文件列表] | 验证：[命令] [结果]
```

**Tier 2（中等任务）**：
```
**完成**：[1-2句摘要]
**变更**：[文件: 函数/原因]
**验证**：[通过项/总数]
```

**Tier 3（复杂任务）**：完整交付，包含变更摘要、验证结果、需求覆盖度对照表、升级路径、遗留风险

### 交付规则
- [MUST NOT] 验证失败时交付；先进入修复或升级流程
- 对 bug/排查类任务必须说明：最终命中问题层、为何非其他层、如何证明根因闭合
