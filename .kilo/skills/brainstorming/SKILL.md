# 将想法转化为设计

## 何时触发

**任何创造性工作之前必加载**，包括但不限于：
- 创建新功能/组件
- 添加功能
- 修改行为
- 即使是 TODO 列表、单个工具函数、配置变更

## 硬门（HARD-GATE）

```
未呈现设计且用户未批准 = 禁止调用任何实现 skill / 写代码 / 脚手架 / 实现动作
```

**适用于每个项目，无论多简单**。

## 反模式：太简单不需要设计

每个项目都走此流程。todo 列表、单函数工具、配置变更——全是。**简单项目正是未审视假设造成返工的高发区**。设计可以很短（真正简单的几句话），但必须呈现并获得批准。

## 9 步 Checklist

1. **项目上下文**：读 AGENTS.md / 入口目录 / 最近 commits
2. **澄清问题**：模糊术语（用户/账户/任务/会话）逐一定义，一次一个
3. **方案提议**：每重要决策列 2-3 个可选方案，问"如果不选这个会怎样"
4. **设计呈现**：用具体边界值测试方案可行性，给推荐答案
5. **规格文档**：短设计门 → 方案+验收点；完整规划 → DAG+依赖+风险
6. **审查循环**：交叉验证用户声称的架构与实际代码，发现矛盾直接指出
7. **用户签字**：方案须经 coderAgent 转用户确认或按授权放行
8. **计划生成**：签字后才进"计划输出"段
9. **触发 writing-plans**：T2 完整规划后，输出可执行任务清单

> T1 短设计门可压缩为前 3 步；T2 完整规划必须全 9 步。

## 设计原则

- **一次一问**：不要一次性多问
- **多选优先**：选项比开放问题更易答
- **YAGNI 铁律**：剔除所有不必要功能
- **探索替代**：永远 2-3 个方案
- **增量验证**：呈现一段获批一段
- **灵活回溯**：用户有疑问时回去澄清
- **隔离清晰**：每个单元单一职责、明确接口、可独立测试

## 设计输出

每个单元必须可答：
- 它做什么？
- 怎么用？
- 它依赖什么？

可在不读内部的情况下理解单元 = 边界良好。

## 规格自审（写完文档后）

1. **占位符扫描**：TBD/TODO/不完整/模糊？修
2. **内部一致性**：章节互相矛盾？架构与功能描述不符？
3. **范围检查**：是否可一个 plan 实现？是否需分解？
4. **歧义检查**：某要求有 2 种解读？选一种并显式说明

修完内联，无需再审。

## 用户复审门

写完规格后必须问：

> "Spec 已写入并提交到 `<path>`。请审阅，如有改动请告知，然后再开始写实现计划。"

等用户响应。请求改动 → 改 + 跑规格自审循环。仅在批准后继续。

## 终止状态

**唯一终态：调用 writing-plans**。禁止调用 frontend-design / mcp-builder 或任何其他实现 skill。

## 红旗（Red Flags）

- 跳过设计直接编码
- "太简单不需要设计"
- 一次性多问
- 未列替代方案直接给推荐
- 设计未获批就开 plan
- 多规格模糊（用户/账户/任务/会话）
- 设计文档含 TBD/TODO

## 反模式

- **"太简单"借口**：单函数工具也要过
- **同时多问**：淹没用户
- **不探索替代**：直接给"显然"方案
- **设计后未审就 plan**：跳过规格自审
- **用户未批就开 plan**：违反硬门
- **泛泛设计**："让系统更好"→ 不可验证
- **不切分大项目**：多独立子系统应拆为子项目，每个走 spec→plan→实现

## "太简单"借口反驳表（硬门）

| 借口 | 反驳 |
|------|------|
| "就一个 config 改动，3 行代码" | 3 行也可能改错关键值。设计门可压缩为 1 段（5-10 句），但必须有过 |
| "是 todo 列表，不需要设计" | todo 列表也有"完成定义"——什么算一项？粒度？状态？"完成"怎么验？这些就是设计 |
| "改个文件名/路径" | 改路径涉及：调用方、文档、测试、CI 脚本。漏一个 = 静默 bug |
| "用户已经说清楚了" | 用户说清楚 ≠ 用户审视过方案。设计门是让用户**批准方案**，不是让用户**重新描述需求** |
| "我先做，做完用户再 review" | review = 验收 ≠ 设计批准。事后 review 改方案 = 浪费已完成的工作。设计门 5 分钟节省返工 30 分钟 |

**反模式红旗**（输出含以下词立即 STOP，回看硬门）：
"太简单不用设计""一行代码改完""user 说了就照做""做完再 review""config 改动不算任务"

## 大项目分解

若需求含多个独立子系统（"建一个含 chat/文件存储/账单/分析的平台"）：

1. **立即标记**：不要花问题细化需先分解的项目
2. **协助分解**：哪些独立部分？相互关系？建设顺序？
3. **走子项目流程**：每个子项目独立 spec→plan→实现
