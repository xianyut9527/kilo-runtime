# UI Design Lab Skill — 设计探索工作流

> **适用场景**：不确定最佳设计方案、需要探索多种变体、从用户反馈中迭代、做 A/B 测试前准备。
> **核心流程**：访谈 → 发现 → 变体 → 测试 → 精炼 → 决策
> **黄金法则**：若项目**已有设计评审流程或设计系统**，在现有框架内进行探索；本 skill 提供探索方法论。

## 1. 设计访谈（Discovery Interview）

在动手设计前，先回答以下问题，产出**设计简报（Design Brief）**：

### 用户与场景
- [ ] 目标用户是谁？（角色、技术水平、使用频率）
- [ ] 用户在什么场景下使用这个功能？（紧急/悠闲、移动端/桌面）
- [ ] 用户的核心痛点是什么？（效率？理解？信任？）

### 业务与约束
- [ ] 业务目标是什么？（转化？留存？降低支持成本？）
- [ ] 技术约束是什么？（框架限制、性能预算、时间线）
- [ ] 品牌调性是什么？（专业/ playful / 极简 / 华丽）

### 竞品与参考
- [ ] 用户现在用什么替代方案？（竞品、Excel、邮件、脑内记忆）
- [ ] 同类产品中最受好评的是谁？为什么？
- [ ] 是否有必须避开的设计模式？（用户已厌烦的交互）

### 产出：Design Brief 模板
```markdown
# Design Brief: [功能名]

## 用户
- 角色: [初级用户 / 专业用户 / 管理员]
- 场景: [描述具体使用场景]
- 痛点: [1-3 个核心痛点]

## 业务目标
- 首要: [如：提升转化率 20%]
- 次要: [如：减少客服咨询量]

## 约束
- 技术: [React + Tailwind, 2 周交付]
- 品牌: [SaaS 专业风格，蓝白主色]

## 竞品参考
- 最佳实践: [Linear 的列表交互]
- 反面教材: [竞品 X 的复杂筛选器]

## 成功标准
- [ ] 用户能在 30 秒内完成核心任务
- [ ] 新手用户无需文档即可上手
- [ ] 移动端体验不降级
```

## 2. 生成变体（Generate Variants）

基于 Design Brief，生成 **3-5 个设计方案变体**。每个变体应有明确的设计假设：

### 变体策略
| 变体类型 | 设计假设 | 适合场景 |
|---------|---------|---------|
| **保守型** | 遵循行业惯例，最小学习成本 | B端工具、企业软件 |
| **创新型** | 打破惯例，追求差异化 | 消费产品、创意工具 |
| **极简型** | 功能做减法，核心路径最短 | MVP、高频操作 |
| **丰富型** | 信息密度高， power user 友好 | 数据仪表盘、管理后台 |
| **引导型** | 大量空状态、提示、教程 | 新用户 onboarding |

### 变体输出格式
```markdown
## Variant A: [保守型 — 表格驱动]

### 设计假设
专业用户熟悉表格操作，表格视图提供最高信息密度。

### 关键交互
- 主视图：数据表格，支持排序/筛选/分页
- 操作：行内编辑 + 批量操作工具栏
- 空状态：引导创建第一条记录

### 优势
- 学习成本极低
- 信息密度高
- 与 Excel 导出无缝衔接

### 风险
- 移动端体验差
- 视觉单调，缺乏品牌感

---

## Variant B: [创新型 — 卡片流]
...
```

## 3. 设计评审（Critique）

对每个变体进行结构化评审，使用**多维度评分卡**：

### 评分维度（1-5 分）
| 维度 | 权重 | 评估标准 |
|------|------|---------|
| 可用性 (Usability) | 30% | 用户能否无障碍完成任务？ |
| 视觉吸引力 (Aesthetics) | 20% | 是否符合品牌调性？是否令人愉悦？ |
| 可维护性 (Maintainability) | 15% | 实现复杂度？设计系统兼容性？ |
| 性能 (Performance) | 15% | 加载速度？动画流畅度？ |
| 可扩展性 (Scalability) | 10% | 能否支持未来功能扩展？ |
| 无障碍 (Accessibility) | 10% | WCAG 合规性？键盘导航？ |

### 角色测试（Persona Test）
为每个关键用户角色 walkthrough：
- **新手用户**：能否在无人指导的情况下完成首次任务？
- **专业用户**：能否高效完成批量/复杂操作？
- **移动端用户**：核心功能是否在手机上可用？
- **辅助技术用户**：屏幕阅读器能否理解页面结构？

### 产出：评审报告
```markdown
# Design Review: [功能名]

## Variant A — 表格驱动
| 维度 | 分数 | 备注 |
|------|------|------|
| 可用性 | 4/5 | 熟悉度高，但筛选器对新手不友好 |
| 视觉吸引力 | 2/5 | 过于朴素，缺乏品牌感 |
| ... | ... | ... |
| **加权总分** | **3.4/5** | |

## 推荐决策
选择 **Variant C（混合型）**，原因：
1. 桌面端用表格保证效率
2. 移动端自动切换为卡片视图
3. 保留品牌色彩和微交互提升质感
```

## 4. 反馈精炼（Refine via Feedback）

将评审结果和选定变体交付给用户/利益相关方，收集反馈并迭代：

### 反馈收集清单
- [ ] "这个设计解决了你的核心痛点吗？"
- [ ] "有什么操作让你感到困惑或犹豫？"
- [ ] "有没有遗漏的重要信息或功能？"
- [ ] "与现有方案相比，这个更好还是更差？为什么？"
- [ ] "如果只能改一个地方，你会改什么？"

### 迭代规则
- **P0 反馈**（阻碍使用）：必须修改
- **P1 反馈**（显著影响体验）：优先修改
- **P2 反馈**（个人偏好）：记录但不保证修改
- **意见冲突**：回到 Design Brief 中的用户画像和业务目标做决策

### 精炼循环
```
交付变体 → 收集反馈 → 识别模式 → 生成改进版 → 再次评审 → 决策
```
- 通常需要 **2-3 轮**精炼才能达到满意方案
- 每轮变更必须记录：**改了什么 → 为什么改 → 基于谁的反馈**

## 5. 决策与文档化

### 最终决策模板
```markdown
# Design Decision: [功能名]

## 选定方案
[Variant X — 简述核心设计模式]

## 决策依据
1. [用户测试显示 90% 新手能在 30 秒内完成核心任务]
2. [利益相关方一致认可移动端体验]
3. [实现复杂度在 2 周时间线内可控]

## 被否决的方案及原因
- Variant A: [移动端体验差，不适合目标用户]
- Variant B: [实现复杂度过高，超出时间线]

## 待验证假设
- [假设 1：用户会频繁使用批量操作功能]
- [假设 2：卡片视图在移动端足够清晰]

## 后续迭代计划
- V1.1: [根据上线数据优化筛选器]
- V1.2: [添加高级用户的键盘快捷键]
```

### 将决策转化为代码
- 根据最终方案更新 DESIGN.md
- 提取可复用组件和 token
- 在实现前输出**组件 API 设计文档**

## 6. Agent 执行检查清单

- [ ] 是否先完成了 Design Brief（用户/业务/约束/竞品）？
- [ ] 是否生成了 >= 3 个有明确假设的变体？
- [ ] 是否使用了多维度评分卡进行评审？
- [ ] 是否为关键用户角色做了 walkthrough？
- [ ] 是否收集了结构化反馈而非笼统意见？
- [ ] 是否记录了变更原因和反馈来源？
- [ ] 最终决策是否有清晰的依据和否决理由？
- [ ] 是否输出了组件 API 设计文档再开始编码？

---

> **核心思想**：好的设计不是想出来的，是**试出来**的。Design Lab 提供的是系统性的试错框架，避免凭直觉做设计决策。
